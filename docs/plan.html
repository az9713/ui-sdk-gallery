Plan · 23 November 2026

A plan for 100 UIs that show the range of UI SDK

Status, 24 November 2026: the build is complete, with 103 UIs. Open the gallery. The text below is the plan as written before the build.

This is a plan. At the time of writing, no UI was built. Each UI gets a position on the 3 orthogonal axes. A coverage rule decides what must be in the set. This page gives the set, the decisions, and the reasons.

55shipped components, each used a minimum of 1 time
50stateful behaviors, each used a minimum of 1 time
5layers of axis 3, each with UIs (layer 1 is provisional)
7non-empty cells of the Map grid, each with evidence
5adapters, for 1 primitive

All counts are from the npm packages @ui-sdk/core and @ui-sdk/web at version 0.1.0-beta.16, which I installed and inspected on 23 November 2026. Section 7 says how I counted.

1 · The answer in short

One set, 100 positions, no repeated idea

  • Axis 3, layer. The set has UIs at each of the 5 layers, from a new behavior to a change of look only. Layer 1 is provisional (see set C).
  • Axis 1, role. Each of the 100 UIs has a Build face and a Use face. The agent bridge connects to each UI.
  • Axis 2, kind of help. Mechanism, knowledge, check and control each have evidence on the page. The empty cell Build × Control stays empty.
  • Coverage rule. The set uses each of the 55 shipped components and each of the 50 stateful behaviors a minimum of 1 time.
  • No padding. Each UI must add 1 component, behavior, public entry or documented capability that no other UI adds. The same UI in a different subject does not count.
  • With the 6 decisions of section 6, the build is 100 UIs plus 3 comparison builds that do not use UI SDK. The total is 103.
2 · How I arrived at the set

Six steps

  1. The axes sort offerings, so each UI needs a record

    The 3 orthogonal axes of the Map tab sort the 11 offerings of UI SDK. They do not sort UIs. A UI is not "the bridge" or "the testing kit". A UI uses them.

    Thus each UI gets a record with 3 values: the lowest layer where code must be written for it (axis 3), and the 1 cell of role × kind of help that the UI exists to show (axes 1 and 2).

  2. "Versatile" must be a claim that a reader can check

    A count of 100 proves nothing. 100 settings forms show 1 ability 100 times. So I replaced the count with a rule: the set must use each item of the package's own lists.

    The lists come from the package, not from me: 55 component pages, 50 behaviors whose names start with create or bind, 5 adapters, 5 layers, and the documented functions of the agent bridge.

  3. 52 rows carry a list item, and 30 rows are my allocation

    I first set the size of each set: 30, 40, 4, 5, 5 and 16. After that, I counted what each row carries. 52 rows each carry an item of the 2 counted lists that no other row carries. 30 rows are my allocation to layers 1, 3 and 5 and to the Use column.

  4. 18 rows extend the lists

    The number 100 was given. The 2 counted lists are complete after 52 rows, and my allocation adds 30. I gave each of the other 18 rows (7 in set A, 11 in set B) an item of the package that the 2 lists do not contain.

    52 is not a proven minimum. A different author could cover the 55 components with fewer than 23 screens.

    Examples: @ui-sdk/core/date (A24), server rendering (A27), announce for screen-reader messages (B21), position (B34), fuzzyScore (B38). The table in section 4 marks these rows "extends".

  5. A test build changed 3 parts of the design

    Before I fixed the design, I built 1 page with 4 controls. Three results changed the plan:

    • The no-build path has no bridge. The package's browser bundle does not contain createAgent. Thus the gallery needs a bundler (Vite).
    • The bridge is not smaller on a small page. The bridge snapshot was 432 bytes. The accessibility-tree text for the same 4 controls was 291 bytes. Thus each card must show a measurement, not a claim.
    • A removed component stays in the snapshot with offPage: true. Thus the gallery loads 1 UI for each page load.

  6. A review removed the rows that broke my own rule

    • 10 rows added nothing new. For example, a second createTransfer list and a second createViewport plan. I replaced each with a row that adds a public entry or helper.
    • 1 row was counted 2 times. The Web Components picker of set D was the same UI as B20. Set D now has 4 other adapters and 1 page that puts all 5 under 1 bridge.
    • My 2 ideas for set C are already in the package. createRovingFocus with wrapping covers a circle, and scrubTo has snap points. Set C is provisional until a search finds 2 behaviors that the package does not ship.

5 · Why it shows versatility

The argument has 4 parts

Part 1. The set changes on 7 dimensions, and each has evidence that can fail

Part 2. The dimensions are independent: one can change while the others stay the same

The set has pairs of UIs that differ on 1 dimension only. This is the same test that makes the 3 axes orthogonal.

  • Only the adapter changes: B20 against D01 to D04. The primitive file is the same.
  • Only the look changes: A01 against E01 to E05. The markup is the same.
  • Only the role changes: the Build face and the Use face of each card. The UI is the same, and a person or an agent operates it.
  • Only the control changes: F12 to F15 add 1 attribute or 1 callback to parts that already work.
  • Only the component changes (planned): I plan to use createGridFocus in a seat map (B01), a spreadsheet (B04), an emoji picker (B19) and a crossword (B36), and createRovingFocus in a log viewer (B13), a metro map (B17) and a piano (B35).

The last pair type is the central claim of UI SDK: 1 behavior goes into many different components, and 1 component uses several behaviors (B06 uses 3). The table in section 4 names only the first use of each behavior. The coverage script will report the real count of uses after the build.

Part 3. No single UI can make the claim, and no set is spare

One UI has 1 layer and a small number of behaviors. Range is a property of a set. If you remove 1 set, 1 claim loses all its evidence:

RemoveClaim with no evidence left
Set AThe 55 shipped components work together in real screens.
Set BAn agent can build components that UI SDK does not ship. This is the main promise of the launch post.
Set CThe lowest layer can get a new behavior.
Set DThe behavior is the same in each framework.
Set EThe look is separate from the behavior.
Set FEach function of the bridge and each agent control has a UI that shows it.

Part 4. All 100 use the same small set of parts

Range with a different tool for each job is not versatility. The 100 UIs use these parts:

  • 1 core package, @ui-sdk/core, plus 1 adapter package for each framework. 95 UIs use only the Web Components adapter. Set D adds the other 4 adapters.
  • 1 function for each own component, definePrimitive, in sets B, C and D and in F07 to F09. The skill says that the shipped components of set A are built from the same behaviors.
  • 1 bridge, createAgent, and 1 testing kit.

The test build installed 2 packages (core and the Web Components adapter). They have no dependencies of their own.

What the set does not show

  • Visual design range. UI SDK gives behavior, not design. The reviewer said his result looked "AI heavy". The gallery uses 1 design system.
  • A benefit against no UI SDK. Range is not benefit. The 3 comparison builds of decision 3 give a small comparison: 3 UIs, 1 attempt each.
  • A live model. Scripted steps and tests exercise the bridge. No model drives it.
  • A screen reader. checkPattern checks ARIA roles, states and keys. It does not run a screen reader.
  • Real phones. The touch UIs run in desktop Chrome with touch emulation.
  • Speed or cost. The gallery measures bytes, not seconds or dollars.
6 · The 6 decisions

My recommendation is the selected option for each

The recommendations were accepted. Each decision below gives the selected option, the reason, and the option that I did not select.

1

Start with a pilot of 6 UIs

Selected: build A01, B01, B04, D01, E03 and F12 first, then stop for a review.

Reason: the cost of 1 UI is not known. The pilot has 1 small primitive (B01), 1 large primitive (B04) and 1 second adapter (D01), so the measurement includes the high-cost cases.

Not selected: all 100 in 1 run. An error in the shell or the gates would then repeat in 100 files.

2

Web Components for the main gallery

Selected: Web Components for sets A, B, C, E and F. Set D shows the other 4 adapters.

Reason: the test build verified this path, and it needs no framework compiler. The claim about 5 adapters gets its own set, so it does not need 100 UIs in 5 frameworks.

Not selected: React for all 100. It adds a framework to each file and shows nothing more about UI SDK.

3

Add 3 comparison builds with no UI SDK

Selected: build A01, B01 and B17 again with the same model and the same request, with no UI SDK and no mention of the keyboard. The total is 103 builds.

Reason: the 100 UIs show range. They do not show a difference against plain code. The review video used this method on 1 map. The build with no UI SDK had 15 separate Tab stops and no tests.

Limit: 3 UIs with 1 attempt each is a small sample. The page will say so.

4

TypeScript for the UI files

Selected: TypeScript, with the type check as gate 1.

Reason: the skill says that TypeScript requires the handlers that each slot role needs, such as focus for a role that takes focus. The agents write the files, so a person does not write TypeScript.

Not selected: JavaScript. The test build used JavaScript and passed. Thus I did not test the type checks, and the pilot is their first test.

5

One agent for the pilot, parallel subagents after it

Selected: I build the pilot alone. In phase 2, a maximum of 3 subagents work at the same time, each on 1 batch of 10 UI files. No live-model race.

Reason: each UI is 1 independent file, so parallel work is safe. Subagents use more tokens, because each one reads the docs again. The pilot gives the number that shows if this cost is acceptable.

In my first reply I gave no recommendation here. This is new, and the question comes again with the pilot numbers before phase 2.

6

git init in the gallery folder

Selected: yes, in gallery/ only.

Reason: the project folder is not a git repository. About 110 new files would have no undo.

8 · Build order and gates

Four phases, with a stop after the pilot

The system

  • 1 new folder, gallery/, with exact versions of the 2 packages.
  • 1 file for each UI. It holds the primitive, the mount function, the card data and the tests.
  • 1 shell that finds the UI files. It mounts 1 UI for each page load.
  • Vite writes 1 script and 1 stylesheet. The page opens from disk and can go into 1 new Artifact.
  • Estimated file count: about 110.

The 4 gates for each UI

  1. Type check.
  2. Tests: keyboard test and agent test. For a primitive: also checkPattern, checkServer, checkDirection, and a count of deliberate breaks that the tests caught.
  3. Real browser: no console error, Tab through all controls, 1 screenshot, contrast 4.5:1 for text and 3:1 for control edges.
  4. impeccable detect on the built page: 0 findings.

What each UI card shows

  1. The UI, live.
  2. Its position on the 3 orthogonal axes, with the same words as the Map tab.
  3. Build face: the 1-sentence request, the behaviors or components used, and the line count.
  4. Check face: the test results of gate 2.
  5. Use face: the live snapshot() text, its byte count, and a button that runs a scripted act task.
  6. Measurement: snapshot bytes against accessibility-tree bytes, with the label "my measurement". A browser tool records the second number at build time.
9 · Risks and open points

What can change the plan

Risks

  • Beta. Version 0.1.0-beta.16 came out on the day of this plan. The plan pins the exact version.
  • Set C. The 2 new behaviors are not selected. If no missing behavior exists, set C becomes 4 more rows of set B, and layer 1 has no UI. The gallery then says so.
  • Docs gaps. When the docs do not answer, the skill says to write a small test. Each gap goes in the report.
  • jsdom limits. Popups, layout and focus between fields need the real browser gate.
  • Label matches. The bridge matches a label by its words, so "Tip" and "Custom tip" collide. Each UI needs unique control names.
  • Cost. Not known until the pilot.

Differences between the package and the Map tab

The Map tab came from 4 sources. The package shows more. I did not change the Map tab.

  • "50+ behaviors": the tables list 134 helpers. 50 start with create or bind.
  • Starter library: 55 components, not the 12 that the website shows.
  • On the Use side, not on the Map: a change log (Observe), history and undo, a preview of a suggestion, and a model that runs on your server.
  • A candidate for the empty cell Build × Control: strict mode and typed slot roles stop some wrong builds. My reading: these are checks, so the cell stays empty. This is an open decision.
  • The skill and the docs are in the npm package.

Sources: the 4 summaries in this project (review video, launch post, repository README, website), and the npm packages @ui-sdk/core, @ui-sdk/web and @ui-sdk/react at 0.1.0-beta.16.

My inferences, not source claims: the record of 3 values for each UI, the 6 sets and their sizes, the 7 dimensions, the split into 52, 30 and 18 rows, and the comparison of 432 bytes against 291 bytes.
